# E2EE 安全复查与后续检查清单

日期：2026-10-13。范围：当前工作区源码、客户端配置、本地 Windows 下载包。

本次进行了代码检查和本地安装包签名检查，没有攻击线上服务，没有完成双客户端渗透测试，也没有扫描完所有依赖。代码缺口与实际利用结果必须区分。上一轮源码修复尚未同步发布到现有安装包。

## 安全边界

### 本轮修复状态

下文保留初始检查证据，并非当前代码仍全部存在这些缺口。源码已补齐通话信令签名、撤回/已读签名、当前群成员名单的独立核对与本地签名批准、会话撤销的活动连接检查、锁屏附件任务清理、CSP、Android 备份排除、下载来源限制和部署管理凭据要求。

群名单批准不等于管理员签名的全局成员协议；首次信任仍需独立核对。前向保密、泄露后恢复、Windows 发行者签名和真实设备/双客户端发布验收仍未完成。现有下载包尚未更新。部署步骤及兼容性限制见 `encryption-security-v2.md`。

至少覆盖三类攻击者：普通恶意用户、被攻破的中转服务器、取得本地数据或应用执行权限的攻击者。服务器正常时的权限检查不能替代客户端的密码学身份验证。应用已解锁时任意代码执行或操作系统被攻破，超出了单纯锁屏能够保护的边界。

## 已确认的问题与防护缺口

### 1. 高优先级：通话信令没有身份认证

证据：`frontend/src/stores/call.js:271` 直接发送 SDP，`:350`、`:582`、`:631`、`:654` 将收到的 SDP 交给 `setRemoteDescription`。没有绑定长期身份公钥的签名，也没有独立校验对方 DTLS 指纹。

影响：媒体传输由 WebRTC 加密，但恶意信令服务器仍可能替换握手信息建立两段连接。不能将当前通话实现描述为抵抗恶意服务器的已认证 E2EE 通话。此处是协议检查结论，尚未完成中间人演示。

修复方向：签名并验证 offer、answer、重协商和 ICE restart 的会话上下文及 SDP 指纹，绑定发起方、接收方、call ID 和协商序号，防止重放及跨通话替换。签名身份使用已固定并核对的公钥。

验收：替换 SDP 指纹、转发其他通话的 answer、重放 restart、错误身份签名均应终止通话；正常直连和 TURN 中继都应通过。

参考：[RFC 8827](https://www.rfc-editor.org/rfc/rfc8827.html)。

### 2. 高优先级：群成员名单没有端到端认证

证据：`frontend/src/stores/group.js:31` 从服务器拉取名单，`:49` 生成收件人集合；`frontend/src/stores/chat.js:2719` 开始群消息发送，按该名单包装内容密钥。

影响：固定已知成员公钥能阻止替换旧成员的密钥，却不能阻止被攻破的服务器伪造一个新成员。新身份会作为首次见到的身份接受，发送方随后可能为它包装群消息密钥。消息签名不解决收件人集合被篡改的问题。

修复方向：明确群管理权限，由客户端验证签名的成员增删记录、群身份、成员名单版本和密钥 epoch；成员变化后更新相应的加密状态。可结合经过审查的群协议设计。

验收：伪造新增成员、恢复旧成员名单、踢人后重放旧群状态、不同成员看到不同名单，都不得静默发送群密钥。

### 3. 高优先级：令牌撤销没有覆盖已有 WebSocket

证据：`backend/internal/handler/identity.go:114` 退出时只调用 `RevokeSession`，且没有处理返回错误。`backend/internal/handler/ws.go:170` 仅在握手中验证令牌，创建的 `ws.Client` 不携带可用于持续验证的会话信息。`backend/internal/ws/hub.go:729` 的消息循环没有检查令牌是否撤销。

影响：持有撤销前已建立连接的攻击者，不一定会被服务器及时断开。消息签名能限制伪造加密内容，但不能代替会话撤销，尤其是通话、撤回和其他控制功能。尚需真实连接验证撤销后的可用操作。

修复方向：将连接绑定会话及其版本；退出、身份恢复、撤销设备时主动关闭相应连接，并在关键操作或定时检查时重新验证；Redis 撤销失败不得返回成功。

验收：先连接后退出、过期、恢复身份、删除账号，原连接应及时失效；Redis 故障时不得谎报退出成功。

### 4. 需要补充修复：锁屏后的附件任务仍保存敏感元数据

证据：`frontend/src/stores/chat.js:1912` 的接收传输记录保存完整 `metadata`，其中包括附件 `fileKey`。`:780` 的 `lockLocalData` 清除了消息及历史密钥缓存，但没有清除传输记录；暂停任务也会保留部分闭包数据。

影响：上一轮锁定加固不等于所有敏感内存都已清除。具备应用上下文读取能力的代码，在锁定后可能仍取得活跃附件任务的密钥。该结论不表示远程用户能够直接读取这些内存。

修复方向：锁定时中止任务并清除敏感传输状态，解锁后从已保护的存储重建，而非依赖保留明文密钥的任务恢复。检查图片预览、Blob URL、文件句柄和备份对话框。

验收：下载中、上传中、预览中、导出私钥中触发锁定，任务状态中不得保留可用的敏感密钥；解锁后能安全恢复。

### 5. 完整性缺口：撤回等控制事件仍依赖服务器

证据：`frontend/src/stores/chat.js:2927` 的撤回处理只检查标识格式并删除本地记录，没有验证撤回发起者的密码学签名。群撤回和已读触发的阅后即焚也需要同类检查。

影响：普通用户仍受后端权限检查约束；被攻破的服务器可能伪造控制事件，影响消息保留和可用性。签名正文不能保护未签名的撤回、已读和成员管理事件。

修复方向：定义哪些控制操作必须端到端签名，绑定操作者、会话、目标消息、操作类型和防重放数据。

### 6. 客户端防护缺口：缺少 CSP，Android 备份范围未明确限制

证据：`frontend/src-tauri/tauri.conf.json:23` 设置 `csp: null`；已检查的网页和 Nginx 配置也没有 CSP。`frontend/src-capacitor/android/app/src/main/AndroidManifest.xml:6` 开启 `allowBackup`，没有配置明确的备份/迁移排除规则。

影响：缺少 CSP 是纵深防御缺口，不等于已发现可利用的 XSS。Android 的实际备份内容、WebView 数据和设备迁移行为需要实机检查，不能仅凭配置断言私钥已泄露。

修复方向：为网页、Tauri、Android 分别设置可实际运行的 CSP；审查文章 HTML 清洗、外链、WebView 导航和本地插件权限。明确排除身份、令牌、聊天数据库及设备加密数据的系统备份，保留用户主动的私钥备份流程。

参考：[Tauri CSP](https://v2.tauri.app/security/csp/)、[Android Auto Backup](https://developer.android.com/identity/data/autobackup)。Android 部分厂商的设备迁移行为不能仅靠 `allowBackup=false` 控制，需要同时审查 extraction rules。

### 7. 发布与管理面缺口

- 本地 `downloads/yunChat.exe` 的 `Get-AuthenticodeSignature` 检查返回 `NotSigned`。需要发行者签名和发布流程保护；同一下载服务器上的 SHA-256 文件本身不能证明发行者身份。
- `frontend/src/services/native-update.mjs:15` 只要求更新 URL 使用 HTTPS，没有固定允许的下载来源；需要明确允许的域名与路径。
- `docker-compose.yml:51` 将管理密码写成固定值。需要区分开发/生产配置并移除生产默认密码；本次没有确认线上实际运行的密码。
- Android 构建已配置 release signing，但当前 APK 的签名证书、debug/release 状态及与历史版本的证书一致性仍需实际验证。
- `backend/config.yaml` 被 Git 跟踪，需要审查其中真实凭据及历史提交；本报告不复制凭据值。

## 仍未解决的协议能力

前向保密和泄露后恢复能力尚未实现，详见 `docs/encryption-security-v2.md`。不能因 AES-GCM、临时 ECDH 密钥或新增签名就宣称已获得这些属性。

初次身份关联仍采用首次使用信任，需要通过独立渠道核对安全码。公钥登记还需要检查 P-256/SPKI 格式验证、持钥证明、原子初始化和并发请求下的不可覆盖性。

## 后续需要执行的检查

1. 密码协议：随机数及 nonce 唯一性、KDF 域分离、不同用途密钥隔离、签名覆盖范围、重放和降级、异常密文处理。
2. 附件：越权下载、群成员离开后的权限、分块交换、截断、重复上传、服务器错误报告缺失块、重试期间源文件变化。当前 nonce 由前缀与索引确定，必须保证同一密钥/nonce 不用于不同明文；仅元数据相同不能证明源文件字节相同，但是否可从实际 UI 触发仍需验证。
3. 身份和会话：初始登记、私钥恢复、会话过期、设备撤销、账号注销、重连、WebSocket 限流与令牌泄漏。
4. 本地数据：旧安全码迁移、迁移中断/磁盘满/数据库损坏/多窗口、锁定竞态、系统备份、剪贴板、日志和缓存。
5. 发布链：Windows/APK 签名、签名密钥隔离、HTTPS 下载、独立校验来源、依赖漏洞和供应链、版本回退与新旧协议协调升级。
6. 真实双客户端：在线、离线、群增删成员、跨设备恢复、附件暂停恢复、通话重协商，以及被篡改服务器响应下的失败行为。

现有 TLS 1.2/1.3、HSTS、通用消息通知、服务端日志脱敏、文章 HTML 白名单清洗，以及附件下载身份检查是已有的有效保护。它们不代表上面的端到端信任链已经完整验证。

建议顺序：先处理通话身份认证、群成员认证和会话撤销；同步完成锁定任务清理与发布/备份加固，再推进前向保密协议迁移和独立安全审计。
